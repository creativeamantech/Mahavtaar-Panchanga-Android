# Panchanga Golden Reference Corpus

Status: schema and coverage plan only. No expected astronomical values have been fabricated.

## Purpose

Freeze the active TypeScript engine's outputs before Kotlin migration. Every Kotlin implementation change must be compared against these versioned fixtures. Fixtures must be generated by a pinned source commit and include provenance.

## Required scenario matrix

Create fixtures for each applicable group:

1. **Indian baseline cities:** Bhopal, Indore, Ujjain, Varanasi, Delhi, Chennai.
2. **Longitude/timezone diversity:** London, New York, Singapore, Sydney.
3. **Month systems:** identical date/location under Amanta and Purnimanta.
4. **Ayanamsha modes:** every mode actually exposed by the active Panchanga UI/API, including the default Chitrapaksha/Lahiri mode.
5. **Lunar boundaries:** Tithi start/end, Nakshatra start/end, Yoga and Karana transitions.
6. **Civil-day boundaries:** just before/at/after local midnight and sunrise; pre-sunrise Hindu-day continuity.
7. **Solar edge cases:** long/short daylight, high latitudes, sunrise/sunset search failure or polar-day conditions where supported.
8. **Lunar edge cases:** moonrise/moonset unavailable, events crossing local midnight.
9. **Lunar months:** ordinary, Adhika Masa, and any supported Kshaya Masa cases.
10. **Determinism:** repeat the same input and assert identical raw numeric timestamps and values.

## Comparison policy

- Compare raw absolute timestamps before comparing formatted strings.
- Exact deterministic rule outputs (Hora sequence, Swara lookup tables, interval ratios) must match exactly.
- Astronomical outputs must use a documented tolerance per field; do not apply one broad tolerance to every output.
- Compare event ordering and segment continuity, not just displayed names.
- Check that adjacent segments have no gaps or overlaps unless the source explicitly models one.
- Compare null/unavailable status separately from numeric values.
- Compare formatted local times only after timezone and daylight-saving conversion.
- Never silently normalize a source mismatch. Record it, explain it, and get an explicit decision before changing behavior.

## Fixture capture requirements

The capture utility must:
- call the active source engine at a pinned commit;
- record exact input coordinates, IANA timezone, date, month system, and coordinate selection;
- capture the complete `PanchangaResponse` needed by the three launch modules;
- include source commit SHA and dependency versions;
- produce deterministic, reviewable JSON;
- never use the Android/Kotlin implementation to generate its own expected values.

## Release gate

Do not enable a migrated module by default until:
- the complete fixture suite passes;
- boundary and timezone cases pass;
- no unexplained missing or extra events remain;
- any accepted difference is documented with a rationale and explicit approval.
